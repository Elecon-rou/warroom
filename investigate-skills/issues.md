# Issue and incident investigation
Determine the symptom, affected scope and time window. Start with the user's evidence; discover the actual service and signals. Compare error/latency/traffic behavior and find a small set of relevant logs or traces. Use read-only MCP metadata and bounded samples, not unbounded scans.
Test specific hypotheses with corroborating data from more than one signal where possible. Read the widgets skill and attach useful evidence: metrics for timing/impact, logs for error messages, traces for slow or failing operations. Report what is confirmed, what is only suspected, and the next discriminating check. Do not claim a root cause without supporting evidence. State data gaps. Do not perform configuration changes, restarts or other writes.

Log discovery hit counts can be estimates; do not present them as exact incident counts. A capped log or trace widget is a sample. No matching sample does not prove absence, and observed activity alone does not prove service health.

Diagnostic completion checklist: quantify the symptom and affected population; identify the peak or change inside the selected window; test a leading explanation and at least one credible alternative; correlate a second signal when it can discriminate causes. A broad CPU chart or a few error lines are starting evidence, not a root-cause conclusion. Use explicit LogsQL stats count()/grouped counts to measure error frequency and query relevant metrics for denominators. Identify the concrete failing operation or error pattern where possible. If the selected window lacks a baseline, say so. End with evidence-supported confidence, unresolved gaps and a specific next check, not a generic checklist.
