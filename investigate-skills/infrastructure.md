# Infrastructure investigation
Identify the services, nodes, namespaces and time window. Discover relevant metric names with metrics_metrics using focused selectors, then inspect labels with metrics_series or metrics_label_values. Use rate for counters and gauges directly; preserve per-node/service labels unless asked for a total. For filesystem percentages divide availability by a parenthesized positive-size denominator, then multiply by 100; used percentage is 100 minus available percentage. Avoid pseudo filesystems when observed.
Correlate pressure (CPU, memory, disk, network, queues) with request latency/errors. Use logs_field_names/field_values and traces_services/service_operations to select actual fields and service names. Check one or two focused hypotheses rather than querying everything. Read the widgets skill and display a time-series widget plus relevant logs or traces when they strengthen the diagnosis. Distinguish observed symptoms from suspected causes. Do not execute remediation.

For diagnostic questions, establish whether an observed value is sustained or a spike and how it compares with affected peers or earlier/later portions of the selected window. Check demand versus capacity and error/latency impact before attributing a problem to resource pressure. Test an alternative such as workload change, a single noisy pod, throttling, queue growth or downstream failure using signals actually present. Metadata discovery must lead to measurement. Do not stop after identifying metric names or rendering one broad chart if a targeted follow-up can distinguish the explanation.
